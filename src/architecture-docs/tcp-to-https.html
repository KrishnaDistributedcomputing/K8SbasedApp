🔌 TCP to HTTPS/REST Migration

Moving from raw TCP socket communication between services to HTTPS/REST APIs with proper contracts, observability, and security. Why it matters and how to do it without breaking everything.

Home / Architecture / TCP to HTTPS

The Problem with TCP Port-Based Communication

In the current monolith, internal components communicate via raw TCP sockets on fixed ports. Service A opens a TCP connection to Service B on port 5432, sends a binary payload, and gets a binary response. This works — until it doesn't.

TCP Sockets (Current)

  • Binary protocol — no human-readable debugging
  • Tight coupling: callers must know exact host:port
  • No built-in retries, timeouts, or circuit breaking
  • No authentication/authorization per request
  • No API versioning — any change breaks callers
  • No observability — can't trace requests through the system
  • Firewall rules are port-based: "allow port 5432" = full DB access
  • No content negotiation or schema validation
vs

HTTPS/REST APIs (Target)

  • JSON/Protobuf — human-readable, tooling-friendly
  • Service discovery via DNS/Kubernetes Service
  • Built-in retries, timeouts, circuit breakers (Polly, Istio)
  • JWT/mTLS per-request authentication
  • URL-based versioning: /api/v1/, /api/v2/
  • OpenTelemetry tracing across all requests
  • Fine-grained authorization: "allow GET /patients but not DELETE"
  • OpenAPI schema validation and contract testing
Security risk: TCP port-based communication in Kubernetes means any pod that can reach port 5432 has full database access. There's no query-level authorization. With HTTPS/REST + Istio mTLS, you control access at the API endpoint level: "pharmacy-service can call GET /api/v1/patients/{id}/allergies but not DELETE /api/v1/patients".

Key insight: Not everything should move to REST. Database connections, message brokers, and caches use purpose-built protocols that are more efficient than HTTP. The migration is about service-to-service business logic calls — not infrastructure connections. For infra, just add TLS encryption.

How to Approach the Migration

Phase 1: External-Facing Endpoints (Week 1-2)

Start with what users see. Move all frontend-to-backend communication through HTTPS with TLS termination at the ingress.

Browser HTTP:5000→ Add NGINX Ingress + TLS→ Browser HTTPS:443 → NGINX → Service
# Current: Browser → http://ehr-api:5000/api/patients # Target: Browser → https://api.ehr.example.com/api/v1/patients # Step 1: Create TLS certificate (cert-manager + Let's Encrypt) apiVersion: cert-manager.io/v1 kind: Certificate metadata: name: ehr-api-tls namespace: ehr spec: secretName: ehr-api-tls-secret issuerRef: name: letsencrypt-prod kind: ClusterIssuer dnsNames: - api.ehr.example.com # Step 2: Update Ingress to terminate TLS apiVersion: networking.k8s.io/v1 kind: Ingress metadata: name: ehr-api-ingress annotations: nginx.ingress.kubernetes.io/ssl-redirect: "true" nginx.ingress.kubernetes.io/force-ssl-redirect: "true" spec: tls: - hosts: [api.ehr.example.com] secretName: ehr-api-tls-secret rules: - host: api.ehr.example.com http: paths: - path: /api/ pathType: Prefix backend: service: name: ehr-api port: number: 8080

Phase 2: Service-to-Service via Istio mTLS (Week 3-6)

Install Istio service mesh. Every pod gets an Envoy sidecar that automatically encrypts all pod-to-pod traffic with mutual TLS. No code changes needed.

Pod A TCP:8080 → Pod B→ Install Istio sidecars→ Pod A → Envoy (mTLS) → Envoy → Pod B
# Enable strict mTLS for the entire ehr namespace apiVersion: security.istio.io/v1 kind: PeerAuthentication metadata: name: default namespace: ehr-core spec: mtls: mode: STRICT # Reject any non-mTLS traffic --- # Authorization policy: pharmacy-service can only call specific patient endpoints apiVersion: security.istio.io/v1 kind: AuthorizationPolicy metadata: name: patient-service-access namespace: ehr-core spec: selector: matchLabels: app: patient-service rules: - from: - source: principals: ["cluster.local/ns/ehr-clinical/sa/pharmacy-service"] to: - operation: methods: ["GET"] paths: ["/api/v1/patients/*/allergies"] - from: - source: principals: ["cluster.local/ns/ehr-clinical/sa/clinical-service"] to: - operation: methods: ["GET", "POST"] paths: ["/api/v1/patients/*"]

Phase 3: Encrypt Infrastructure Connections (Week 7-8)

Database, Kafka, and Redis connections stay on their native protocols but add TLS encryption:

PostgreSQL: Already using sslmode=require with Azure PostgreSQL. Connection string includes SSL certificate validation. No change needed.
Kafka: Enable SASL_SSL listener. Configure producers/consumers with security.protocol=SASL_SSL and sasl.mechanism=PLAIN. Use Azure Event Hubs connection string.

Phase 4: Remove Legacy TCP Ports (Week 9-10)

After all traffic flows through HTTPS/mTLS, close the old TCP ports in Kubernetes NetworkPolicy:

# Deny all TCP traffic except HTTPS (443/8080) and infrastructure ports apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: name: deny-legacy-tcp namespace: ehr-core spec: podSelector: {} # Apply to all pods in namespace policyTypes: [Ingress, Egress] ingress: - ports: - port: 8080 # HTTPS service port protocol: TCP - port: 15090 # Istio metrics protocol: TCP egress: - ports: - port: 443 # External HTTPS protocol: TCP - port: 5432 # PostgreSQL (TLS-encrypted) protocol: TCP - port: 9093 # Kafka SASL_SSL protocol: TCP - port: 6380 # Redis TLS protocol: TCP - port: 53 # DNS protocol: UDP

Contract-First API Design

When replacing TCP calls with REST APIs, design the API contract before writing code. This prevents the "just expose whatever the database has" anti-pattern.

Approach: OpenAPI-First

StepActionToolOutput
1Write OpenAPI spec for each serviceSwagger Editor / Stoplightpatient-service.openapi.yaml
2Generate server stubs from specNSwag / openapi-generatorASP.NET Core controllers with contracts
3Generate client SDKs from specNSwag / KiotaTyped HTTP clients for callers
4Contract testing in CIPact / SpectralFail build if API breaks contract
5Version APIs from day oneAsp.Versioning.Mvc/api/v1/, /api/v2/
Why contract-first matters: With TCP sockets, the "contract" is whatever binary format the developer chose. Changing it requires coordinated deploys. With OpenAPI contracts, consumers and producers develop independently — the spec is the agreement. Breaking changes go in a new version.

What You Gain: Observability

HTTP/HTTPS traffic is inherently more observable than raw TCP. After migration you get:

Distributed Tracing

Every HTTPS request carries a traceparent header (W3C Trace Context). Istio sidecars propagate it automatically. You can trace a single patient lookup from browser → APIM → patient-service → database and see exactly where latency lives.

Request-Level Metrics

Istio exports Prometheus metrics for every HTTP request: latency (p50/p95/p99), status codes (2xx/4xx/5xx), request volume. TCP sockets give you... bytes in and bytes out.

Access Logging

Every HTTPS request is logged with: timestamp, source service, destination service, method, path, status code, latency, user identity (from JWT). TCP logs show: "connection opened, connection closed."

Traffic Shifting

With HTTP-aware routing (Istio VirtualService), you can send 10% of traffic to a new version for canary testing. TCP only knows ports — it's all-or-nothing.
