🔌 TCP to HTTPS/REST Migration

Moving from raw TCP socket communication between services to HTTPS/REST APIs with proper contracts, observability, and security.

Why TCP Port-Based Communication Is a Problem

TCP Sockets (Current State)

  • Binary protocol — no human-readable debugging
  • Tight coupling: callers must know exact host:port
  • No built-in retries, timeouts, or circuit breaking
  • No per-request authentication or authorization
  • No API versioning — any change breaks callers
  • No distributed tracing or request-level metrics
  • Port-based firewall rules: "allow port 5432" = full DB access
  • No content negotiation or schema validation
vs

HTTPS/REST APIs (Target State)

  • JSON/Protobuf — human-readable, tooling-friendly
  • Service discovery via DNS / Kubernetes Service
  • Polly + Istio provide retries, timeouts, circuit breakers
  • JWT + mTLS per-request authentication
  • URL-based versioning: /api/v1/, /api/v2/
  • OpenTelemetry W3C Trace Context across all calls
  • Fine-grained: "allow GET /patients but not DELETE"
  • OpenAPI schema validation + contract testing
Security risk: TCP port-based communication in Kubernetes means any pod that can reach port 5432 has full database access. There is no query-level authorization. With HTTPS/REST + Istio mTLS, access is controlled at the API endpoint level — pharmacy-service can call GET /api/v1/patients/{id}/allergies but cannot call DELETE /api/v1/patients.

Not everything moves to REST. Database, broker, and cache connections use purpose-built protocols that outperform HTTP for their use case. The migration targets service-to-service business logic calls.

TLS Termination at Ingress

All external traffic enters through NGINX Ingress with TLS termination. cert-manager automates certificate lifecycle via Let's Encrypt.

Service-to-Service mTLS via Istio

Istio injects an Envoy sidecar proxy into every pod. All pod-to-pod traffic is automatically encrypted with mutual TLS — zero application code changes required. Combined with AuthorizationPolicy, each service's API surface is locked down to specific callers and HTTP methods.

Pod A → Pod B (plaintext TCP)→ Pod A → Envoy sidecar (mTLS) → Envoy sidecar → Pod B

PeerAuthentication — Enforce mTLS

apiVersion: security.istio.io/v1 kind: PeerAuthentication metadata: name: default namespace: ehr-core spec: mtls: mode: STRICT # Reject any non-mTLS traffic

AuthorizationPolicy — Fine-Grained Access

apiVersion: security.istio.io/v1 kind: AuthorizationPolicy metadata: name: patient-service-access namespace: ehr-core spec: selector: matchLabels: app: patient-service rules: - from: - source: principals: - "cluster.local/ns/ehr-clinical/sa/pharmacy-service" to: - operation: methods: ["GET"] paths: ["/api/v1/patients/*/allergies"] - from: - source: principals: - "cluster.local/ns/ehr-clinical/sa/clinical-service" to: - operation: methods: ["GET", "POST"] paths: ["/api/v1/patients/*"]
How Istio identity works: Each pod gets a SPIFFE identity certificate (spiffe://cluster.local/ns/{namespace}/sa/{service-account}) provisioned automatically by istiod. The AuthorizationPolicy matches on these identities — not IP addresses — so policies survive pod restarts and scaling.

Infrastructure Connection Encryption

Database, Kafka and Redis connections stay on their native wire protocols. The goal is adding TLS encryption and authentication — not replacing the protocol.

NetworkPolicy — Close Legacy Ports

After all traffic flows through HTTPS/mTLS, lock down the namespace with a NetworkPolicy that only permits encrypted ports. Any pod trying to use a legacy plaintext port is denied at the kernel level (Calico/Cilium).

apiVersion: networking.k8s.io/v1 kind: NetworkPolicy metadata: name: ehr-core-strict namespace: ehr-core spec: podSelector: {} # Apply to all pods policyTypes: [Ingress, Egress] ingress: - ports: - port: 8080 # HTTPS service port protocol: TCP - port: 15090 # Istio Prometheus metrics protocol: TCP - port: 15021 # Istio health probe protocol: TCP egress: - ports: - port: 443 # External HTTPS (Azure services, APIM) protocol: TCP - port: 5432 # PostgreSQL (TLS required by Azure) protocol: TCP - port: 9093 # Kafka SASL_SSL protocol: TCP - port: 6380 # Redis TLS protocol: TCP - port: 53 # DNS resolution protocol: UDP - port: 53 protocol: TCP - port: 15012 # istiod xDS (control plane) protocol: TCP
Port audit: Before applying, run kubectl exec -it <pod> -- ss -tlnp on every pod to inventory active listeners. Any port not in the NetworkPolicy whitelist will be blocked. Verify with kubectl logs -l app=calico-node -n calico-system for denied connections after rollout.

Typed HTTP Client with Resilience (Polly)

// Program.cs — register typed HTTP client with retry + circuit breaker builder.Services.AddHttpClient<PatientServiceClient>(client => { client.BaseAddress = new Uri("https://patient-service.ehr-core.svc.cluster.local:8080"); client.DefaultRequestHeaders.Add("Accept", "application/json"); }) .AddPolicyHandler(HttpPolicyExtensions .HandleTransientHttpError() .WaitAndRetryAsync(3, attempt => TimeSpan.FromMilliseconds(200 * Math.Pow(2, attempt)))) .AddPolicyHandler(HttpPolicyExtensions .HandleTransientHttpError() .CircuitBreakerAsync(5, TimeSpan.FromSeconds(30))); // PatientServiceClient.cs — typed client public class PatientServiceClient { private readonly HttpClient _http; public PatientServiceClient(HttpClient http) => _http = http; public async Task<PatientDto?> GetPatientAsync(int id) => await _http.GetFromJsonAsync<PatientDto>($"/api/v1/patients/{id}"); public async Task<List<AllergyDto>> GetAllergiesAsync(int patientId) => await _http.GetFromJsonAsync<List<AllergyDto>>( $"/api/v1/patients/{patientId}/allergies") ?? []; }

Observability Gains

HTTP/HTTPS traffic is inherently more observable than raw TCP. Moving to REST unlocks four capabilities that are impossible with binary socket communication:

Distributed Tracing

Every HTTPS request carries a traceparent header (W3C Trace Context). Istio sidecars propagate it automatically. A single patient lookup can be traced: browser → APIM → patient-service → PostgreSQL — with per-span latency breakdown.

# Example trace header (auto-injected by Istio) traceparent: 00-4bf92f3577b34da6a3ce929d0e0e4736-00f067aa0ba902b7-01 # Format: version-traceId-parentSpanId-traceFlags

Request-Level Metrics

Istio exports Prometheus metrics for every HTTP request automatically. No application instrumentation needed.

# Istio-generated Prometheus metrics istio_requests_total{ source_workload="clinical-service", destination_workload="patient-service", response_code="200", request_protocol="http" } 45832 istio_request_duration_milliseconds_bucket{ destination_workload="patient-service", le="50" } 42100 # 92% of requests under 50ms

Structured Access Logging

Every request is logged with: timestamp, source, destination, method, path, status, latency, and user identity from JWT claims. TCP logs only show "connection opened / closed."

{ "timestamp": "2026-03-22T18:30:00Z", "source": "clinical-service", "destination": "patient-service", "method": "GET", "path": "/api/v1/patients/42/allergies", "status": 200, "latency_ms": 12, "user": "dr.smith@ehr.example.com", "trace_id": "4bf92f3577b34da6a3ce929d0e0e4736" }

Traffic Shifting & Canary

HTTP-aware routing (Istio VirtualService) enables canary deployments — send 10% of traffic to a new version while 90% stays on the current version. TCP only knows ports: it's all-or-nothing.

apiVersion: networking.istio.io/v1 kind: VirtualService metadata: name: patient-canary spec: hosts: [patient-service] http: - route: - destination: host: patient-service subset: v1 weight: 90 - destination: host: patient-service subset: v2 weight: 10
