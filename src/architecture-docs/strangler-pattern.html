🌿 Strangler Fig Pattern

Gradually replace a monolithic EHR application with microservices — one bounded context at a time — without a risky "big bang" rewrite. Named after the strangler fig tree that grows around its host until it fully replaces it.

What Is the Strangler Fig Pattern?

In a tropical forest, a strangler fig seed lands in the canopy of a host tree. It grows roots down the trunk, gradually enveloping the host. Over years, the fig becomes self-supporting and the host tree decomposes inside — replaced entirely, with zero disruption to the forest ecosystem.

In software, the pattern works identically:

  1. Place a facade (API gateway/proxy) in front of the monolith — all traffic goes through it
  2. Build a new microservice for one bounded context (e.g., Patient Management)
  3. Route that context's traffic from the monolith to the new service
  4. Repeat for the next bounded context until the monolith is empty
  5. Decommission the monolith — it's been "strangled"
Why not a big-bang rewrite? Rewrites fail. In healthcare, a failed rewrite means clinicians lose access to patient records. The strangler pattern delivers value incrementally — each migrated service is independently deployable, and the monolith keeps running for everything not yet migrated.

How to Approach This Migration

Step 1: Install the Facade (Week 1-2)

Place NGINX Ingress + Azure APIM in front of the monolith. Initially, 100% of traffic proxies straight to the monolith. Nothing changes functionally — this just gives you the routing control you need.

Browser→ APIM / Ingress (facade)→ Monolith (100% of traffic)

Step 2: Pick the First Slice (Week 3)

Choose the first bounded context to extract. The ideal first candidate has these properties:

CriterionWhy It MattersBest First Candidate
Fewest inbound dependenciesFewer callers = fewer things to redirectPatient Service (everyone reads from it, few write to it)
Clear data ownershipSingle database table cluster = clean extractionPatients + Allergies + Vitals = one aggregate
Well-defined API surfaceExisting REST-ish endpoints = less design work/api/v1/patients already exists

Our choice: Patient Service is the first extraction target. It owns 3 tables (patients, allergies, vitals), has the clearest API surface, and is primarily read-heavy. If something goes wrong, we flip the route back to the monolith in 10 seconds.

Step 3: Build the New Service (Week 4-8)

Build the Patient microservice alongside the monolith. Both run simultaneously.

What the new service needs:

  • ASP.NET Core 8 Web API with its own PostgreSQL database
  • Same API contract as the monolith's patient endpoints
  • Data migrated from monolith's ehrdb.patients table
  • Event publishing to Kafka on every write
  • Health check endpoint for readiness probe

What stays in the monolith:

  • Everything except patient CRUD
  • The monolith still reads patient data (via API call to new service)
  • Monolith's patient table becomes read-only (stale copy for fallback)
  • If new service is down, monolith serves stale data with a warning

Step 4: Dual-Write + Data Sync (Week 6-8)

Before switching traffic, set up dual-write so both databases have the same data:

Write request→ New Patient Service→ patient-db (primary)
PatientCreated event→ Kafka→ Sync consumer→ monolith ehrdb (secondary)
Critical: During dual-write, the new service's database is the source of truth. The monolith's copy is updated asynchronously via Kafka events. This means there's a brief window (RPO) where the monolith's copy lags behind. For patient reads, this is acceptable — it's only stale by seconds.

Step 5: Traffic Shift — Canary (Week 9)

Use Istio VirtualService or APIM to gradually shift traffic from monolith to the new service:

Step 6: Decommission Monolith Slice (Week 10)

Once 100% of patient traffic is on the new service for 2 weeks with zero issues:

  1. Stop the dual-write sync consumer
  2. Drop the patients/allergies/vitals tables from the monolith's ehrdb
  3. Remove patient controller code from the monolith
  4. The monolith is now smaller — one bounded context extracted

Full Migration Sequence — 6 Bounded Contexts

Each extraction follows the same 5-step pattern. Here's the recommended order:

Phase 1: Patient Management (Month 1-2)

3 tables (patients, allergies, vitals). Read-heavy, clear boundaries. Proves the pattern works. Monolith shrinks from 8 to 5 tables.

Phase 2: Provider Management (Month 3)

1 table (providers). Simple extraction — providers are reference data with low write volume. Monolith: 4 tables.

Phase 3: Scheduling (Month 4-5)

1 table (appointments). Depends on Patient and Provider references — consumes their events via anti-corruption layer. Monolith: 3 tables.

Phase 4: Clinical Encounters (Month 6-7)

1 table (medical_records). Most complex extraction — encounters reference patients, providers, prescriptions, and labs. Use ACL to resolve cross-references. Monolith: 2 tables.

Phase 5: Pharmacy (Month 8)

1 table (prescriptions). Drug interaction checks call Patient Service for allergies — a well-defined API boundary. Monolith: 1 table.

Phase 6: Laboratory (Month 9-10)

1 table (lab_results). Final extraction. After this, the monolith has zero tables and can be decommissioned. Monolith: gone.

Anti-Corruption Layer (ACL)

When a new microservice needs data from the monolith (or vice versa), don't let the monolith's data model leak into the new service. Use an Anti-Corruption Layer — a translation boundary that converts between the two models.

Example: Clinical Service Needs Patient Data

// Anti-Corruption Layer in Clinical Service // Translates monolith's patient model to clinical service's domain model public class PatientAclClient : IPatientReference { private readonly HttpClient _http; // Calls Patient Service REST API public async Task<ClinicalPatient> GetPatientForEncounter(int patientId) { // Call new Patient Service (or monolith during transition) var response = await _http.GetAsync($"/api/v1/patients/{patientId}"); var dto = await response.Content.ReadFromJsonAsync<PatientDto>(); // Translate external model to clinical domain model // Only take what clinical service needs — not the entire patient return new ClinicalPatient { PatientId = dto.PatientId, FullName = $"{dto.FirstName} {dto.LastName}", ActiveAllergies = dto.Allergies .Where(a => a.IsActive) .Select(a => new AllergyFlag(a.Allergen, a.Severity)) .ToList(), DateOfBirth = dto.DateOfBirth // Note: we don't import insurance info — clinical doesn't need it }; } }
Key principle: Each microservice owns its own view of external data. The clinical service doesn't store a copy of the patient record — it stores a ClinicalPatient projection with only the fields it needs. If the Patient Service changes its model, only the ACL adapter changes.

Risks and How to Mitigate Them

RiskImpactMitigation
Data inconsistency during dual-writeMonolith and microservice return different data for same patientShadow comparison: run both and diff responses for 100% of traffic. Alert on any divergence.
Performance regression (network hop)Monolith's in-process call becomes HTTP call (1-5ms latency)Pre-measure: instrument current in-process call latency. Set budget: new service must be within 2x of original.
Team doesn't finish migration (stuck at 50%)Half-monolith/half-microservice = worst of both worldsTime-box each phase to 2 months. If a phase takes longer, it's a sign you sliced too big — split it.
Rollback needed after cutoverUsers on new service, data in new DB, can't go backKeep dual-write running for 2 weeks after 100% cutover. Monolith can serve stale reads as fallback.
Cross-context transactionsMonolith uses DB transactions across tables; microservices can'tReplace with saga pattern: distributed workflow with compensation. Accept eventual consistency.
