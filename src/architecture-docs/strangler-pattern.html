🌿 Strangler Fig Pattern

Gradually replace a monolithic EHR application with microservices — one bounded context at a time — without a risky "big bang" rewrite. Named after the strangler fig tree that grows around its host until it fully replaces it.

What Is the Strangler Fig Pattern?

In a tropical forest, a strangler fig seed lands in the canopy of a host tree. It grows roots down the trunk, gradually enveloping the host. Over years, the fig becomes self-supporting and the host tree decomposes inside — replaced entirely, with zero disruption to the forest ecosystem.

In software, the pattern works identically:

  1. Place a facade (API gateway/proxy) in front of the monolith — all traffic goes through it
  2. Build a new microservice for one bounded context (e.g., Patient Management)
  3. Route that context's traffic from the monolith to the new service
  4. Repeat for the next bounded context until the monolith is empty
  5. Decommission the monolith — it's been "strangled"
Why not a big-bang rewrite? Rewrites fail. In healthcare, a failed rewrite means clinicians lose access to patient records. The strangler pattern delivers value incrementally — each migrated service is independently deployable, and the monolith keeps running for everything not yet migrated.

Migration Approach

Step 1: Install the Facade

Place NGINX Ingress + Azure APIM in front of the monolith. Initially, 100% of traffic proxies straight to the monolith. Nothing changes functionally — this gives you the routing control needed for per-path traffic splitting.

Browser→ APIM / Ingress (facade)→ Monolith (100% of traffic)
apiVersion: networking.k8s.io/v1 kind: Ingress metadata: name: ehr-facade annotations: nginx.ingress.kubernetes.io/rewrite-target: /$2 spec: rules: - host: api.ehr.example.com http: paths: # Initially: everything goes to monolith - path: /api(/|$)(.*) pathType: ImplementationSpecific backend: service: name: ehr-monolith # Changes per-path as services are extracted port: number: 8080
After first extraction: The Ingress gains a second path rule sending /api/v1/patients to the new Patient Service while all other paths continue to the monolith. Each subsequent extraction adds one more path rule.

Step 3: Build the New Service

Build the microservice alongside the monolith. Both run simultaneously — the facade controls which gets traffic.

New Service Requirements

  • ASP.NET Core 8 Web API with its own PostgreSQL database
  • Same API contract as the monolith's endpoints
  • Data migrated from monolith's tables
  • Domain event publishing to Kafka on every write
  • Health check + readiness probe endpoints
  • OpenTelemetry instrumentation from day one

Monolith Changes

  • All other bounded contexts remain unchanged
  • Monolith reads extracted data via API call to new service
  • Monolith's copy of extracted tables becomes read-only
  • If new service is down, monolith serves stale data + warning header
  • Add X-Data-Source: fallback header for stale responses

Step 4: Dual-Write Data Synchronization

Before switching traffic, set up event-driven dual-write so both databases stay in sync. The new service's database is the source of truth; the monolith's copy is updated asynchronously via Kafka.

Write request→ New Patient Service→ patient-db (primary)
PatientCreated event→ Kafka→ Sync consumer→ monolith ehrdb (secondary)
// Kafka event published on every Patient write public record PatientChangedEvent( string EventType, // "Created" | "Updated" | "Deleted" int PatientId, PatientDto Snapshot, // Full current state DateTime OccurredAt, string CorrelationId // Links to originating request trace ); // Sync consumer in monolith updates its read-only copy public class PatientSyncConsumer : IHostedService { public async Task ProcessAsync(PatientChangedEvent evt) { switch (evt.EventType) { case "Created": case "Updated": await _monolithDb.UpsertPatientReadCopy(evt.Snapshot); break; case "Deleted": await _monolithDb.MarkPatientInactive(evt.PatientId); break; } } }
Consistency window: During dual-write, the monolith's copy lags behind by the Kafka consumer lag (typically < 2 seconds). For patient reads this is acceptable. For safety-critical writes (prescriptions referencing allergies), the microservice is always the authoritative source.

Step 6: Decommission Monolith Slice

After full cutover with zero issues over the validation period:

  1. Stop the dual-write Kafka sync consumer
  2. Drop the extracted tables from the monolith's ehrdb
  3. Remove the extracted controller code from the monolith codebase
  4. Archive the monolith's read-only copy as a backup
  5. The monolith is now smaller — one bounded context extracted
Point of no return: Only drop the monolith tables after verifying: (1) zero traffic to monolith endpoint for this context, (2) all downstream consumers use the new service, (3) dual-write consumer has been idle for the full validation period. Keep a pg_dump of the dropped tables for 90 days.

Extraction Sequence — 6 Bounded Contexts

Each extraction follows the same 6-step pattern above. Order is determined by dependency graph — extract leaf nodes (fewest dependencies) first.

OrderBounded ContextTablesDependenciesComplexityMonolith After
1 Patient Management patients, allergies, vitals None (leaf node) Low — read-heavy, clear aggregate 8 → 5 tables
2 Provider Management providers None (reference data) Low — simple CRUD, low write volume 5 → 4 tables
3 Scheduling appointments Patient (read), Provider (read) Medium — cross-context reads via ACL 4 → 3 tables
4 Clinical Encounters medical_records Patient, Provider, Pharmacy, Lab High — most cross-references, needs ACL for 4 contexts 3 → 2 tables
5 Pharmacy prescriptions Patient (allergies for drug interaction check) Medium — safety-critical allergy lookup 2 → 1 table
6 Laboratory lab_results Patient (read), Provider (read) Medium — final extraction, monolith decommissioned 1 → 0 (done)
Dependency rule: A service can only be extracted after all services it depends on are already extracted (or have stable APIs in the monolith). Patient and Provider are leaf nodes — extract them first. Clinical Encounters has the most dependencies — extract it last among non-leaf nodes.

Anti-Corruption Layer (ACL)

When a microservice needs data from another service (or the monolith during transition), the external model must not leak into the consuming service's domain. The ACL is a translation boundary — an adapter that converts external DTOs into the consuming service's domain objects.

Why ACL Is Required

Without ACLWith ACL
Clinical service imports PatientDto with 30 fieldsClinical service defines ClinicalPatient with 4 fields it actually needs
Patient Service adds a field → clinical service breaksPatient Service changes model → only the ACL adapter is updated
Clinical database stores redundant insurance, address, phone dataClinical database stores only PatientId, FullName, Allergies, DOB
Test mocks require full 30-field patient objectTests mock IPatientReference with 4-field projection

ACL Interface

// Domain interface — clinical service defines what it needs public interface IPatientReference { Task<ClinicalPatient> GetPatientForEncounter(int patientId); Task<IReadOnlyList<AllergyFlag>> GetActiveAllergies(int patientId); } // Domain model — only fields clinical service cares about public record ClinicalPatient( int PatientId, string FullName, IReadOnlyList<AllergyFlag> ActiveAllergies, DateTime DateOfBirth ); public record AllergyFlag(string Allergen, string Severity);

ACL Implementation — HTTP Adapter

// Infrastructure layer: translates Patient Service API → clinical domain model public class PatientAclClient : IPatientReference { private readonly HttpClient _http; public PatientAclClient(HttpClient http) => _http = http; public async Task<ClinicalPatient> GetPatientForEncounter(int patientId) { // Call Patient Service REST API var response = await _http.GetAsync($"/api/v1/patients/{patientId}"); response.EnsureSuccessStatusCode(); var dto = await response.Content.ReadFromJsonAsync<PatientDto>(); // Translate: external model → clinical domain model return new ClinicalPatient( PatientId: dto!.PatientId, FullName: $"{dto.FirstName} {dto.LastName}", ActiveAllergies: dto.Allergies .Where(a => a.IsActive) .Select(a => new AllergyFlag(a.Allergen, a.Severity)) .ToList(), DateOfBirth: dto.DateOfBirth // Insurance, address, phone — deliberately excluded ); } public async Task<IReadOnlyList<AllergyFlag>> GetActiveAllergies(int patientId) { var patient = await GetPatientForEncounter(patientId); return patient.ActiveAllergies; } } // DI registration with resilience builder.Services.AddHttpClient<PatientAclClient>(c => c.BaseAddress = new Uri("https://patient-service.ehr-core.svc.cluster.local:8080")) .AddTransientHttpErrorPolicy(p => p.WaitAndRetryAsync(3, attempt => TimeSpan.FromMilliseconds(200 * Math.Pow(2, attempt))));

Key principle: Each microservice owns its own projection of external data. Pharmacy needs allergies + weight for drug interaction checks. Scheduling needs phone number for reminders. Neither service stores the full patient record — only the fields it needs via its own ACL.

Risks and Mitigations

RiskImpactMitigation
Data divergence during dual-writeMonolith and microservice return different data for same queryShadow comparison: run both paths and diff 100% of responses. Alert on any divergence > 0.
Latency regressionIn-process call → HTTP call adds 1-5ms per hopBaseline before migration. Set latency budget: new service p99 must be < 2x original.
Stalled migration (stuck at 50%)Half-monolith / half-microservice = worst of both worldsSet a go/no-go checkpoint per context. If extraction stalls, the bounded context is too large — split it.
Rollback after cutoverData in new DB, can't revert trafficKeep dual-write running after 100% cutover. Monolith can serve stale reads as immediate fallback.
Cross-context transactionsMonolith uses DB transactions spanning multiple tablesReplace with saga pattern: distributed workflow with compensating actions. Accept eventual consistency.
ACL proliferationToo many ACL adapters, each with different caching/retry logicShared ServiceClientBase<T> with standard Polly policies. Each ACL only defines the model mapping.
