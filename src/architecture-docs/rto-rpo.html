⏱️ RTO / RPO Requirements

Recovery Time Objective and Recovery Point Objective define how fast we recover and how much data we can afford to lose. These are the two most critical numbers in disaster recovery planning.

What Are RTO and RPO?

RTO — Recovery Time Objective

How long can the system be down? RTO is the maximum acceptable duration between a failure and service restoration. If your RTO is 15 minutes, you have 15 minutes from the moment the system goes down to the moment patients can use it again.

Think of RTO as: "The hospital can function without the EHR for X minutes before patient safety is at risk."

RPO — Recovery Point Objective

How much data can we lose? RPO is the maximum acceptable amount of data loss measured in time. If your RPO is 5 minutes, the worst case after recovery is that you lose the last 5 minutes of data entry (prescriptions, vitals, notes).

Think of RPO as: "After recovery, the most recent X minutes of patient data might be missing and needs to be re-entered."

Service Tier Classification

Not every service needs the same recovery guarantees. A prescription service going down is life-threatening; a reporting dashboard being slow is inconvenient. We classify services into four tiers:

TierRTORPOServicesAvailability SLAWhy This Tier
Tier 0 — Critical < 1 min 0 (zero data loss) Patient Service, Pharmacy Service 99.99% (52 min/year) Patient identity and active prescriptions are life-critical. An incorrect or missing allergy record during prescribing can cause death.
Tier 1 — High < 5 min < 1 min Clinical Service, Lab Service 99.95% (4.4 hrs/year) Active encounters and lab results must be available quickly. Clinicians can briefly use paper fallback but not for long.
Tier 2 — Standard < 15 min < 5 min Scheduling Service, Notification Service 99.9% (8.8 hrs/year) Missed appointment reminders are annoying but not dangerous. Scheduling can fall back to phone for 15 minutes.
Tier 3 — Low < 1 hr < 30 min Audit Service, Reporting, Analytics 99.5% (1.8 days/year) Audit logs are append-only and can be replayed from Kafka. Reports can wait. No patient care impact.

How to Approach RTO/RPO in This Architecture

Meeting RTO/RPO targets requires a layered strategy across compute, data, and networking. Here's the approach for each layer:

Step 1: Classify Every Service

Walk through each microservice with clinical stakeholders and ask: "If this service is down for X minutes, what happens to patient care?" The answer determines the tier. Don't guess — clinicians know which workflows are critical.

Action: Create a service catalog spreadsheet. For each service, record: service name, owning team, tier, agreed RTO, agreed RPO, data store, backup frequency. Get sign-off from both engineering and clinical leadership.

Step 2: Design Data Protection per Tier

TierDatabase StrategyBackup ApproachReplication
Tier 0 Azure PostgreSQL Flexible Server with zone-redundant HA Continuous WAL archiving to Azure Blob (every transaction) Synchronous replication to standby in different AZ. Automatic failover < 30 seconds.
Tier 1 Azure PostgreSQL with same-zone HA Point-in-time restore (PITR) with 5-minute granularity Asynchronous replication. RPO up to 1 minute of transactions.
Tier 2 Single PostgreSQL instance Automated daily backups + PITR No replication. Restore from backup if instance fails.
Tier 3 Single instance, relaxed I/O Daily backup, 7-day retention None. Rebuild from Kafka event replay if needed.

Step 3: Design Compute Redundancy

TierAKS StrategyPod ReplicasPDB (PodDisruptionBudget)Node Spread
Tier 0 Multi-AZ node pool, priority class = system-critical Min 3 replicas minAvailable: 2 topologySpreadConstraints across 3 AZs
Tier 1 Multi-AZ node pool Min 2 replicas minAvailable: 1 Anti-affinity across nodes
Tier 2 Standard node pool 2 replicas minAvailable: 1 Preferred anti-affinity
Tier 3 Spot instances allowed 1-2 replicas None No constraint

Step 4: Implement Failover Testing

RTO/RPO numbers are meaningless unless tested. Schedule chaos engineering exercises:

Monthly: Kill a random pod of a Tier 0 service. Measure time to full recovery. Must be < 30 seconds (Kubernetes auto-restart + readiness probe). Record actual RTO.
Quarterly: Simulate AZ failure by cordoning all nodes in one zone. Measure time for pods to reschedule to remaining zones. Verify zero downtime for Tier 0/1 services.
Semi-annually: Full DR rehearsal. Restore Tier 0 databases from backup to a new region. Measure actual RPO (compare last backup timestamp to failure time) and actual RTO (time to serve first request).
Annually: Tabletop exercise with clinical staff. Walk through a scenario: "The Canada Central region is completely offline. What's the manual fallback? How do clinicians access patient records?"

PostgreSQL HA Configuration (Tier 0)

# Enable zone-redundant HA for patient-db (Tier 0) az postgres flexible-server update \ --resource-group rg-aks-store-demo \ --name patient-db-canadacentral \ --high-availability ZoneRedundant \ --standby-availability-zone 2 # Verify HA status az postgres flexible-server show \ --name patient-db-canadacentral \ --query "{HA: highAvailability.mode, State: highAvailability.state, StandbyAZ: highAvailability.standbyAvailabilityZone}" # Configure backup retention (35 days for Tier 0) az postgres flexible-server update \ --name patient-db-canadacentral \ --backup-retention 35

Kafka Event Replay for Tier 3 Recovery

# Audit service can rebuild its entire state from Kafka # Topic retention: 30 days for audit events # Consumer group: audit-service-rebuild # Reset consumer offset to beginning (full replay) kafka-consumer-groups.sh --bootstrap-server kafka:9092 \ --group audit-service-rebuild \ --topic ehr.audit.events \ --reset-offsets --to-earliest --execute # Process rate: ~50,000 events/min # Full rebuild of 30-day audit log: ~2 hours

Key metric: Track "actual RTO" and "actual RPO" from every incident and failover test. Plot these against targets. If actuals are consistently close to targets, your margins are too thin — tighten the architecture.

Cost vs. Recovery Tradeoff

Tighter RTO/RPO costs more. Here's the real cost impact per tier:

TierDB Cost MultiplierCompute Cost MultiplierWhy
Tier 02.5-3x (HA + sync replication + premium storage)3x (3 pods, priority scheduling)Synchronous replication doubles I/O cost. Three AZ-spread pods need 3x compute.
Tier 11.8-2x (HA + async replication)2x (2 pods)Async replication is cheaper. Two pods is standard for HA.
Tier 21x (single instance + backup)2x (2 pods for rolling deploy)Backups are included in Azure PG pricing.
Tier 30.7x (spot-eligible, relaxed I/O)1x (single pod OK)Spot instances save 60-80%. Kafka replay replaces backup need.
Decision framework: Start with Tier 2 for every service. Promote to Tier 1 or 0 only after clinical risk assessment. Never start at Tier 0 — it's 3x the cost and you'll run out of budget before you have real data on what actually needs it.
